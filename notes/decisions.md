## Milestone 0 — setup & research

- 2026-09-05 — Target architecture is 2-Step RAG (retrieve once, then generate), not agentic RAG — because a fixed control flow gives a stable baseline to measure hybrid search and reranking against; an agent loop adds variance that would make those deltas unattributable.
- 2026-09-05 — Build order locked to naive → hybrid → rerank → RAGAS — because each stage must be measured against the previous one; building them together makes it impossible to attribute an improvement to any single change.
- 2026-09-05 — Chose FeTaQA (pdfQA-Benchmark) as the corpus — because its Wikipedia tables are a known failure mode for character-based chunking, so the chunking milestone produces visible, teachable breakage rather than silently-mediocre results.
- 2026-09-05 — Verified all LangChain import paths empirically against the venv instead of trusting docs or tutorials — because langchain 1.4 moved retrievers to langchain-classic and deleted `langchain.retrievers`; a tutorial-sourced import would fail at the hybrid-search milestone.
- 2026-09-05 — Recorded langchain-community as sunset (archived 2026-06-19) and planned to hand-roll BM25 / PDF loading rather than import from it — because three load-bearing components on an archived dependency is a client-facing risk, and writing BM25 by hand teaches the scoring function that hybrid search depends on.
- 2026-09-05 — Chose CLAUDE.md over a memory file for project context — because CLAUDE.md is version-controlled, travels with the repo, and is loaded automatically each session; memory is per-machine and invisible to anyone else reading the project.

- 2026-09-06 — Flagged synthetic eval-set generation as the actual billable skill, to cover after milestone 4 — because clients supply an unlabeled PDF folder with no questions, answers, or relevance labels, so consuming a benchmark is training wheels for producing one.

## Milestone 0 — dataset selection (all nine surveyed)

- 2026-09-06 — Rejected FinanceBench despite its domain fit — because it has only 13 QA pairs against 116k chunks (one question = 7.7 points of score movement), and its questions name the company, year and exact financial statements, so retrieval is given away and the benchmark actually measures arithmetic.
- 2026-09-06 — Rejected ClimateFinanceBench — because 30 docs with only 3 distractors makes retrieval trivial, and one reference answer is literally "Not available in the retrieved information", a pipeline failure message leaked into the answer key.
- 2026-09-06 — Rejected ClimRetrieve — because answers are yes/no (median 2 chars), so a coin flip scores 50% and retrieval improvements are undetectable.
- 2026-09-06 — Rejected PaperTab (19 QA), NaturalQuestions (18 QA) — too few questions to resolve any delta. Noted PaperTab has `None` answers testing unanswerable-question abstention, a real production concern worth revisiting with a larger source.
- 2026-09-06 — Rejected Tat-QA as primary despite 1369 QA pairs — because only 65 distractors over 170 docs makes doc-level retrieval too easy, and clustering (max 56 questions on one filing) means effective retrieval sample size is nearer 105 than 1369.
- 2026-09-06 — Chose FinQA as primary — because it has the best retrieval properties in the benchmark: 393 questions over 592 distractors with questions spread thin (median 2/doc, max 7), keeping effective sample size near 393, in the financially-relevant domain.
- 2026-09-06 — Keep FeTaQA as a development sandbox — because at 24k chunks it re-indexes in minutes, and chunking work needs dozens of iterations that would be unaffordable against FinQA's 256k chunks. Develop on FeTaQA, report on FinQA.
- 2026-09-06 — Keep PaperText text only (42MB) — because at 1025 distractors over 27k chunks it has the best distractor-to-cost ratio in the benchmark and a different domain, giving a cheap check on whether the retriever generalizes or overfits to financial filings.
- 2026-09-06 — Stage PDFs for FinQA only — because the parsing milestone runs on the primary dataset, and text is cheap (~490MB total) while PDFs are not.
- 2026-09-06 — Narrowed the keep-set to FinQA + FeTaQA only, dropping PaperText — user's call; the cross-domain generalization check is deferred, recoverable later by re-downloading one folder.
- 2026-09-06 — Copy `real-pdfQA.parquet` into `data/` before any deletion, unconditionally (even on dry runs) — because it sits one level above everything being deleted, is 1.7MB, and its loss makes the remaining 4GB of documents unevaluable.
- 2026-09-06 — Delete `.git` before the datasets when pruning in place — because git-LFS holds a second copy of every tracked file (12.9GB, over half the total), so removing datasets while keeping `.git` reclaims far less and leaves ~700 deletions staged in the working tree.
- 2026-09-06 — Prune script is dry-run by default with an explicit `--apply` — because a 22GB irreversible delete should require a deliberate second action.

## Milestone 0 — corpus sampling and compute budget

- 2026-09-06 — Start with FinQA gold-only (196 docs, ~49k chunks) rather than the full 788 — because "gold" is per-question: with 393 questions over 196 docs, each question faces 195 distractors, and those are *hard* negatives (same domain, structure and vocabulary), so gold-only is both methodologically sound and harder than the larger FeTaQA corpus.
- 2026-09-06 — Treat the 592 held-back distractors as a difficulty dial, adding them in steps later — because a recall-vs-corpus-size curve (196 -> 788 docs) is a stronger result than any single number.
- 2026-09-06 — Compute budget set by an i3-1215U / 8 threads / ~8GB free / no GPU: full FinQA is ~43 min per index build vs ~8 min gold-only — because a 43-minute rebuild stops experimentation, which is a learning failure, not just a slow one.
- 2026-09-06 — Distractor sample must be fixed (seeded, filenames written to disk, reused verbatim across every experiment) and gold must never be sampled — because resampling between runs compares scores from two different benchmarks, and dropping a gold doc makes its questions unanswerable, reporting a data bug as a retrieval failure.
- 2026-09-06 — Flagged for milestone 2: `rank_bm25` is pure Python and holds tokenized corpus plus term-frequency dicts in memory (~1-2GB at 49k chunks, likely OOM at 256k on 8GB) — so the keyword index, not the vector index, sets the corpus ceiling on this machine.

## Milestone 0 — FinQA data characteristics (verified)

- 2026-09-06 — FinQA answers are computed, not extracted: `32%` = (132-100)/100 from the ORLY table, `-7.4%` = (26.3-28.4)/28.4 from the VRTX sentence; neither string appears in its document — because FinQA is a numerical-reasoning benchmark whose retrieval step only has to surface the passage holding the inputs.
- 2026-09-06 — Report retrieval metrics (context recall/precision) for milestones 1-3 and do not tune against answer correctness on FinQA — because derived answers make answer correctness largely a test of the LLM's arithmetic, which retrieval changes barely move.
- 2026-09-06 — Verified `source_text` is normalized, not verbatim: document has `Depreciation ... $25.4 million,` while source_text has `depreciation ... $ 25.4 million ,` (lowercased, spaces before punctuation, space after `$`); row 0's table is reconstructed markdown appearing nowhere in the document — pre-LLM tokenizer output retained by the benchmark.
- 2026-09-06 — Never use string containment (`source_text in chunk`) as a recall check — because normalization guarantees it is always False, reporting 0% recall on a working retriever.
- 2026-09-06 — Build a free numeric-overlap proxy recall metric for the inner loop (fraction of numeric tokens from source_text present in retrieved chunks) alongside RAGAS for reporting — because numbers and entity names survive normalization intact, and on this hardware a free metric runnable every experiment beats an expensive one runnable twice.

- 2026-09-12 — Reranking will use the Bedrock Rerank API rather than a local cross-encoder — because it keeps the whole pipeline cloud-native for the portfolio and removes a GPU dependency from the deployed path.

- 2026-10-06 — Traced RecursiveCharacterTextSplitter._split_text: separator is chosen by PRESENCE in the text (re.search), the whole text is split on it at once, and recursion descends INTO an individually-oversized piece with weaker separators — there is no backtracking and no running-total forward scan
- 2026-10-06 — The 621/622 table seam is not a splitter bug: separator priority assumes a line break is a point of loose semantic coupling, which is inverted in a flattened table where the newline between a label and its value is the tightest coupling in the document — so no chunk_size setting avoids it, only parsing can
- 2026-10-06 — chunk_size is a maximum, not a target: the greedy merge buffer flushes early whenever an oversized piece interrupts it, producing runt chunks (13 chars at size 60 in the trace) that get embedded as full-weight vectors — check chunk length first when a retrieval result looks nonsensical
- 2026-10-06 — CORRECTION to the chunk-size framing: cost is a tiebreaker, not a driver. Chunk size is chosen by eval score; cost only decides between sizes that measure the same. Bigger chunks lose findability, not content — all sizes store the same 78,008,165 characters
